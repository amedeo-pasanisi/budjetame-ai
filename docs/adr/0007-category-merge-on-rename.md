# Renaming a Category onto an existing name merges the two Categories

Renaming a Category to the name of an existing same-Type Category used to fail with "A category with this name already exists." (CategoryNameTaken). It now merges instead: the existing Category survives with its name, icon, and color, the renamed Category's Transactions move to it, and the renamed Category is deleted. The collision response carries the target Category's id and the transaction count so the frontend can confirm the destructive move before it happens. A collision is always same-Type by construction (names are unique per Type), so a rename can never merge across expense/income. Considered and rejected: keeping the error (the user wanted the merge), and an explicit "Merge into…" picker (same backend operation; can be added later without changing the model). The merge is unreversible, so the confirmation with counts is part of the design, not a nicety. API shape: a colliding rename answers 409 with a structured detail carrying `target_id` and `transaction_count`; the confirmed merge is POST /categories/{id}/merge with `{ "target_id": … }`, returning the surviving Category — one atomic write.
