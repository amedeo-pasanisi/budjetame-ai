# Transactions store an optional Place reference alongside coordinates

A Transaction's Geographic Location used to be coordinates only, with the maps link built from them on the frontend and "never stored as text" (US 3.2). Now that the Google picker lets the user choose a place by name or by tapping the map, the pick's name and Google place_id are stored on the Transaction (two nullable columns, written and cleared together), so the "Open in Google Maps" link can open the place's info panel (`google.com/maps/search/?api=1&query=<lat>,<lng>&query_place_id=<id>`) instead of a bare coordinate pin. The link is still built on the frontend, with precedence place_id → name → coordinates, and is never stored. The place_id is a Google-owned opaque string accepted deliberately: a name-search pick or a tap on the Google map can produce a Place — a tap looks up the venue at the tapped point through the Places API (the Leaflet picker stays tap-only; GPS and imports are coordinates-only). Coordinates remain the anchor — a Place without coordinates is outside the model — and re-picking by a coordinates-only pick (Leaflet tap or GPS) or removing the location clears the Place. This deliberately reverses US 3.2's "never stored as text" for the place name; without recording the reversal, a future reader would "fix" the schema back to coordinates-only.

**Amended (maps link form):** the link used to be `google.com/maps/place/?q=place_id:<id>`; the mobile Google Maps apps mis-parse that URL as a search for the literal text `place_id:<id>`, so the phone app never found the place. The link is now Google's documented place-with-pin search URL — `google.com/maps/search/?api=1&query=<lat>,<lng>&query_place_id=<id>` — which the mobile apps run as a search: the coordinates are the query (a pin lands on the spot even when the app ignores the place_id), and the `query_place_id` parameter is a best-effort place card. Desktop behavior is unchanged. A future reader should not "fix" this back to the `place/` URL form.
