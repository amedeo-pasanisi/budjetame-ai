# Transaction search runs server-side because the ledger is paginated

The ledger list is server-paginated (50 rows per page, keyset cursor) — the client never holds the full list, so a keyword search that only filters loaded rows would silently miss matches. Transaction search therefore runs in the database: a new query parameter matches the Transaction's Description as a case-insensitive substring (accents must match exactly), combined with the existing filters and the same cursor pagination, so scrolling continues within the matching set. The Categories tab's search is client-side, but only because categories load fully; do not "unify" the two by making the ledger search client-side. Considered and rejected: a client-side filter over loaded pages (incomplete), and accent-insensitive matching via the `unaccent` extension (extra database dependency; the Categories search is accent-sensitive too, and `unaccent` can be added later without changing the API).
