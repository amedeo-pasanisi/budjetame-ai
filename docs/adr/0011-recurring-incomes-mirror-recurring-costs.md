# Recurring incomes mirror recurring costs

Recurring Incomes (salary-style definitions) are a parallel entity, not a generalization of Recurring Costs: a second table, API resource, and screen side, sharing only the pure recurrence module (`app/recurrence.py`). The alternative — one entity with a `kind` column (cost|income) — was rejected at grilling (issue #59): it would rename a settled domain term (CONTEXT.md, ADR-0010, the `/recurring-costs` API, UI headings), migrate existing data, and churn every shipped test, while the two kinds still diverge in wording ("costs overdue" vs "incomes overdue"). The hard part — occurrence math — was already extracted and shared; what the mirror duplicates is a thin layer of guards and CRUD. If a third kind ever appears, extract the shared service then: the seam is already clean.

**Addendum (2026-11-09).** The "thin layer of guards and CRUD" grew: skips (ADR-0016), per-Occurrence states (ADR-0026), freeze (ADR-0028) and the Budget's due dates each landed twice. The derived-Occurrence reads and the skip write now live once, in the Occurrence Timeline (`app/services/occurrences.py`, CONTEXT.md), parameterised by the kind's two foreign-key columns — the extraction this ADR foresaw. ADR-0033 then collapsed the rest of the mirror: one Recurring definition module per tier, the kind as a value. The decision itself stands: two tables, two resources, two screen sides, two catalogs.

Like the Costs side (ADR-0010), a Recurring Income carries no Wallet and no Category: the definition is name + amount + interval (+ optional start date and due-date override), and the linked Income Transaction chooses its own Wallet and Category at creation time.
