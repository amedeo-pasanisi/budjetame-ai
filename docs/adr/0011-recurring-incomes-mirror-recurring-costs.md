# Recurring incomes mirror recurring costs

Recurring Incomes (salary-style definitions) are a parallel entity, not a generalization of Recurring Costs: a second table, API resource, and screen side, sharing only the pure recurrence module (`app/recurrence.py`). The alternative — one entity with a `kind` column (cost|income) — was rejected at grilling (issue #59): it would rename a settled domain term (CONTEXT.md, ADR-0010, the `/recurring-costs` API, UI headings), migrate existing data, and churn every shipped test, while the two kinds still diverge in wording ("costs overdue" vs "incomes overdue") and gating (expense vs income forms), leaving the "shared" service parameterized by kind everywhere. The hard part — occurrence math — was already extracted and shared; what the mirror duplicates is a thin layer of guards and CRUD. If a third kind ever appears, extract the shared service then: the seam is already clean.
