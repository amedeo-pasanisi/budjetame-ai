# One Recurring definition module per tier; the kind is a value

ADR-0011 made Recurring Incomes a parallel resource to Recurring Costs rather than one entity with a `kind` column: a second table, a second URL prefix, a second screen side, sharing only the pure recurrence module. Its premise was that "what the mirror duplicates is a thin layer of guards and CRUD". Four decisions later that layer was not thin: period-anchored skips (ADR-0016), the per-Occurrence states and skip write (ADR-0026), freezing in place of deletion (ADR-0028) and submit-and-validate forms (ADR-0029) each landed twice, once per side, and after the Occurrence Timeline took the derived reads (ADR-0032) the two copies of everything else still differed by their noun alone: zero code lines between the two routers, zero between the two lifecycle modules, zero between the two frontend api modules, a handful of comment lines between the two forms and the two screens. The copies also drifted in the small ways only duplication allows — an unused import on one side, a docstring on the other still describing the hard delete ADR-0028 replaced — and every future rule would land twice again.

We collapsed the mirror into one **Recurring definition** module per tier (CONTEXT.md), with the kind as a value:

- **Backend.** `app/services/recurring.py` holds the lifecycle — create, update, freeze, unfreeze — once, and a `Kind` table (the model, the noun the rule messages use, the label the HTTP details use, the two foreign-key columns the Timeline reads pins and skips through) is the whole difference between the two kinds as the code sees it; `kind_of(definition)` recovers it from any row, and the Timeline reads its columns from there. `app/recurring.py` builds the HTTP resource for one kind — `make_router(kind)` — and mounts it twice, at `/recurring-costs` and `/recurring-incomes`. The two schema families became one: `RecurringDefinitionCreate`, `RecurringDefinitionUpdate`, `RecurringDefinitionOut`.
- **Frontend.** `RecurringDefinitionForm`, `RecurringDefinitionsScreen` and `RecurringDefinitionModal` take a `side`; `recurringSide.ts` is the side table — the api calls, the catalog prefixes, the Ledger jump kind, the element-id prefix — and the two per-side api modules bind one `recurringDefinitionApi` to their resource path under the names the rest of the app already imports. The Recurring tab's toggle renders the one screen with the side as its `key`.

ADR-0011's decision stands at every level it decided: two tables, two URL prefixes with their own 403/409/422 wording, two screen sides, two catalogs with their own wording. What changed is its premise, and the ADR itself said to "extract the shared service" when that happened.

## Considered Options

- **One entity with a `kind` column** — still rejected, for ADR-0011's reasons: a data migration, renamed domain terms, renamed URLs, every shipped test churned, for no behaviour.
- **Keep the per-kind schema names as empty subclasses of the shared family**, so the OpenAPI component names do not change — rejected: six classes with nothing in them, kept for the names of components no client generates code from (the web client has its own types; the API's JSON is byte-for-byte the same). The one visible change is the component names in `/docs`.
- **Keep the per-side frontend modules as five-line wrappers** (`RecurringCostForm` rendering `RecurringDefinitionForm side="costs"`) — rejected: the wrappers would have no callers but the tests, and a test should render what the app renders.
- **Keep the per-side test files** — rejected for the frontend, where the two suites differed only in fixtures: one suite now runs once per side from a side table (`describe.each`), and the suite gained the assertions the mirror had kept it from writing (the Frozen section after a freeze, the `include_frozen` fetch). Kept for the backend, where the per-kind HTTP suites passing unchanged is the evidence the resources did not change; parametrising them is a separate tidy-up.
- **Fold the Transaction link rules in too** (the four per-kind branches in the Transaction module's update path) — deferred: those branches differ by Transaction type and Transfer direction (ADR-0027), not by noun; they are the Transaction module's rules, not the definition's.

## Consequences

- A rule about a Recurring definition's lifecycle lands in one module on each tier; the two kinds cannot drift.
- `GET/POST/PATCH /recurring-costs…` and `/recurring-incomes…` keep their URLs, bodies, responses and messages; the backend HTTP suites for both kinds, the link, skip, backlog, budget and backup suites passed unchanged. The OpenAPI component names for the wire shapes are now `RecurringDefinitionCreate/Update/Out`; the path parameter is `definition_id`.
- The frontend api barrel keeps every per-side name (`fetchRecurringCosts`, `createRecurringIncome`, …), so every caller and every test that mocks `./api` is untouched; the side table binds those names lazily, so a test that mocks only one side's calls never touches the other's.
- The web Recurring tab renders both sides as before, in both locales; the two sides' strings stay two catalog families.
- Removed: `app/recurring_costs.py`, `app/recurring_incomes.py`, `app/services/recurring_costs.py`, `app/services/recurring_incomes.py`; `RecurringCostForm`, `RecurringIncomeForm`, `RecurringCostsScreen`, `RecurringIncomesScreen`, `RecurringCostModal`, `RecurringIncomeModal`, `recurringCosts.ts`, `recurringIncomes.ts` and their four test files.
