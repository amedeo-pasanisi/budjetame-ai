# Inline entity creation from form selects

Every entity dropdown in the Transaction, Recurring Cost, and Recurring Income forms gains a trailing "＋ Add {entity}…" sentinel option that opens the entity's existing create modal stacked on top of the form; submitting creates the entity, closes only the inner modal, and auto-selects the new entity in the originating field, so the form's draft survives and can be submitted immediately. One shared wrapper component (`EntitySelect`) renders all five sentinel instances — sentinel option always last (after None for optional fields, after the empty-state placeholders), revert-on-pick (the sentinel is never a value: the select returns to what it showed and the wrapper opens the modal), set-on-save (the screen reports the new entity's id back to the open form, whose other fields stay untouched) — so the behavior cannot drift. The screens keep owning the entity lists and their `onSaved` handlers; they host the inner create modals and add the created entity to list state. Modals stack up to two deep (transaction form → recurring cost form), and the shared modal shell now guards Escape with a module-level stack so one keypress closes only the topmost modal — previously every shell listened on `window`, so a single Escape would have closed the whole stack and lost the outer form's draft. Eligibility locking makes auto-select always succeed: the Category create modal accepts a locked type that hides the Type selector and presets it (Expense for expense forms, Income for income forms), and the Wallet create modal accepts an allowed-type restriction (Checking/Credit Card/Cash everywhere except transfer From/To, which also allow Contact). The Recurring Cost and Recurring Income forms carry no entity dropdowns of their own (the definitions never hold a Wallet or Category — ADR-0010), so their sentinels — Category and Wallet — disappeared from them; the transaction form's sentinels for Recurring Cost and Recurring Income themselves remain. The dropdowns are create-only — no edit or delete affordances, which stay in the entity screens. Frontend-only: no backend, schema, or API changes; the create calls reuse the existing endpoints, and link semantics (an Expense auto-linked to a freshly created Recurring Cost pays its oldest Unpaid Occurrence) are unchanged. Rejected: replacing the native selects with a custom dropdown component (kept native per the existing pattern), and letting the forms host their own inner modals (the screens own lists and save paths already, so hosting there reuses them).
